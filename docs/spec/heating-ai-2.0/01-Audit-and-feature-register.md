## Поточна система

Дев'ять Python-модулів AppDaemon й один великий JavaScript-компонент. `HeatingClimate` успадковує `HeatingRecovery` та `Hass`; керування, облік, sampling, observer, публікації, навчання й робота з диском мають спільний runtime та змінювану memory. `heating_model` містить чисту математичну частину, але великий алгоритм пошуку. `heating_stability` утримує/перевіряє план. UI assets генеруються з frontend-файлу. Чинна 0.3.20 вже виносить plan і power advice в executor зі snapshot та single-flight — це корисний захист, який треба зберегти, але процесної ізоляції CPU, диска та глобального AppDaemon lifecycle він не дає.

`save()` у `heating_climate.py:274` записує JSON у .tmp та виконує `os.replace`. Це захист від частково видимого JSON, але в цій функції немає fsync файла/каталогу й транзакції між state, телеметрією та командою. Не встановлено, що дані фактично втрачалися через це; це архітектурний ризик після аварійного живлення.

| Контур | Реальна логіка | Наслідок для заміни |

| HACS coordinator | Зберігає дозволи, зупиняє весь AppDaemon, перевіряє hashes/heartbeat, відновлює | Оновлення опалення зачіпає lifecycle Sky Radar й інших apps; у 2.0 оновлення незалежне |

Точний пошук `climate.kotel`/fan у доступних stored configs не знайшов інших automation/script авторів. Це не виключає прихованих зовнішніх Tuya timers, локального коду або ручних клієнтів. Нативний helper alive може походити з YAML і не був отриманий як flow helper; його повний timeout треба експортувати перед міграцією.

## Передміграційні прогалини доказів

1. Повний актуальний app YAML: startup allow_actuation, source bindings каміна, connection, heartbeats, tariff та зовнішні scripts. Отримати read-only експорт, checksum й карту всіх фактичних авторів команд.
2. Оригінальні state/telemetry/plan snapshots і hashes приватного backup. Без них не перевірено повний replay або точні початкові план/факт за всі дні.
3. Фізична схема фаз/навантажень: local vs input phase labels, signed GRID, неохоплені прилади, токові/напругові межі. Не визначати фазування за friendly_name.
4. Реальна поведінка котла при втраті HA/термостата, антизамерзання, насос/вибіг, автоматичне повернення живлення; незалежний тест OFF і апаратних обмежень.
5. Живий UI не оглянуто в браузері; оцінка структури за кодом, вимогами й попередніми аудитами. Новий SVG є дизайн-концептом із синтетичними даними.
6. Актуальний prompt зовнішнього запланованого кліматичного звіту не читався як чинна задача: доступний контекст свідчить про регулярний аналіз. До міграції звірити його дані/permissions, щоб не залишити зовнішній шлях автоматичної зміни параметрів поза candidate gate. Поточну задачу не змінювати в цьому аудиті.

Ці прогалини не заважають погодити архітектуру. Вони блокують саме фізичне введення/небезпечні припущення; відповідальні кроки й перевірки наведено в документі 06.
