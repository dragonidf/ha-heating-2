# Heating AI 2.0 — architectural approval / рішення власника

**Дата погодження:** 2026-11-03  
**Статус:** ADR01–ADR07 погоджені з чотирма уточненнями нижче.  
**Що дозволено:** підготовка документів, read-only аудит, розробка/тести в окремому репозиторії та ізольованому тестовому середовищі; окремі гілки й PR.  
**Що не дозволено:** будь-які зміни production Home Assistant, чинного `dragonidf/ha-heating-ai`, реального обладнання, автоматизацій, графіків, даних чи розгортання; cutover/activation/physical fault tests без нової окремої явної згоди.

## Погоджені архітектурні рішення (див. `02-Architecture.md`)

- **ADR01:** HA-native control integration + незалежний локальний compute app.
- **ADR02:** один command gateway та fallback всередині HA інтеграції; жодних паралельних автоматичних writers.
- **ADR03:** детермінований планувальник, ШІ лише опційні пояснення/поради поза safety/control path.
- **ADR04:** ізольовані SQLite critical/evidence stores, транзакційність і перевірене відновлення; фактичну сумісність SQLite runtime перевірити на WP0.
- **ADR05:** перенос перевіреної чинної теплової моделі як baseline; challengers не отримують права керування до перевірки.
- **ADR06:** рекуператор/витяжки — лише read-only джерела для моделі; наявні автоматизації не змінювати.
- **ADR07:** локальний snapshot/event/outbox transport із обмеженими чергами, без Redis/Kafka чи зайвих серверів.

## Чотири обов'язкові уточнення власника

1. **Ранковий комфорт.** Зберегти пріоритет передранкового прогріву й мінімум 30 безперервних хвилин, коли потреба є, фізично доступний нагрів і всі safety умови виконані. План не має безслідно зникати через оновлення прогнозу: незмінна базова версія, зміна з причиною й backtesting. Ніякого насильного 30-хвилинного HEAT при надлишку тепла, grid off або ризику перегріву.
2. **Незалежний fallback і ручний пріоритет.** Падіння compute/AI/мережевого API/відкритої панелі не перериває safety-контур. Безпечний автономний fallback, bounded recovery та захист від старих подій. Ручне вимкнення, пауза й фізичне втручання ніколи не перекриваються автоматичним recovery без дозволу власника.
3. **Повнота функціоналу.** Створити трасування `old feature → new requirement → code module → tests → UI/compatibility`. Окремо перевірити значення legacy one-shot при поверненні електрики, сенсори каміна, arbitration нічної/камінної циркуляції й залежності від вентиляції. Рекуператор/витяжки read-only до окремого майбутнього дозволу. Жодної втрати потрібних історій/лічильників/моделі.
4. **UI.** Три прості основні вкладки, читабельна головна, 12h original forecast vs fact, зручний мобільний вигляд, відокремлені експертні функції. Статичний макет не вважається готовим продуктом: потрібні interactive/browser/device checks, доступність і порівняння із затвердженим напрямом.

## Пріоритет і конфлікти

Цей запис є addendum до пакета v1.0, а не заміною його файлів. Якщо нижчі матеріали тлумачаться інакше, Codex фіксує ADR/conflict до реалізації, не змінює P0/P1 у тихий спосіб. Архітектурне схвалення **не** є дозволом на deployment, роботу з реальними thermostat/fan чи зміну production. WP0 виконується лише читанням/аналізом; резервні копії, що потребують запису у production, переносяться на пізніший окремо погоджений gate.
