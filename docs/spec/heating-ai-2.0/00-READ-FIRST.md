# Heating AI 2.0 — пакет для погодження

**Версія документації:** 1.0, 03.11.2026. **Статус:** завершений проєкт, очікує погодження архітектури. Розробку й міграцію не розпочато.

## Висновок для власника

Рекомендована заміна — невелика нативна інтеграція Home Assistant із детермінованим ядром захистів і єдиним виконавцем команд плюс окремий локальний обчислювальний застосунок. Планувальник, навчання, історія та пояснення не можуть затримувати зупинку нагріву. AppDaemon більше не є необхідною залежністю опалення; Sky Radar та інші його застосунки залишаються окремими й не переносяться.

Це свідомо два компоненти, а не набір мікросервісів. Нативна інтеграція потрібна для одного власника команд, автентифікованого UI та резервного керування, що працює при падінні обчислювального застосунку. Повне падіння Home Assistant або зв'язку з термостатом програмний контролер не компенсує: останній рівень — штатні апаратні захисти котла. Їхню фактичну поведінку треба перевірити перед введенням у керування.

## Рішення, які пропонується погодити

1. Два компоненти: HA integration для захистів/команд/UI й локальний compute App для важких задач.
2. Поточні температурні межі, розклади й лічильники імпортуються зі свіжого HA. Історичне бажання 22 °C не замінює чинну ціль 21,5 °C.
3. Перший реліз використовує перевірену детерміновану двостанну теплову модель, а не новий неперевірений ML. Навчання має окрему процедуру допуску.
4. Ранок — не безумовне вмикання на 30 хв: потрібні тепло, придатне живлення і запас до наступного дозволеного нагріву. Безпечний мінімум 30 безперервних хв зберігається, якщо сеанс потрібний і можливий.
5. Перевищення початкового енергоплану дозволяється лише з окремим поясненням зміни потреби; захист від перегріву має пріоритет. Неповні виміри не дозволяють заявляти доведену економію.

## Межі цього результату

Повний поточний локальний AppDaemon YAML, приватні state.json/JSONL та зображення живого UI не отримано: File editor мав стан error, його не запускали й доступ не змінювали. Архітектурні пропозиції та їхні числові SLO — вимоги для майбутньої перевірки, не вже досягнуті показники. Новий контролер не написаний і не протестований як готовий продукт; виконаний аудит старого коду та підготовлена стратегія майбутніх випробувань. Недоступна приватна інформація оформлена як конкретні передміграційні блокери, а не вигадані факти.
